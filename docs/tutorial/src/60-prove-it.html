Cara menjelaskan hasilnya

  • Jika 1 API mentok 100 % dari batas 1 CPU sementara PostgreSQL santai, tier API-lah bottleneck-nya: 2 API seharusnya hampir menggandakan throughput dan meratakan p95. Itu tandanya horizontal scaling bekerja.
  • Jika dari 2 ke 3 hampir tidak membantu, cari bottleneck berikutnya: core laptop yang dipakai bersama semua container, CPU PostgreSQL, db_pool_connections_in_use mentok di 10, Redis yang single thread, Nginx, atau k6 sendiri (cek CPU-nya). Hukum Amdahl: percepatan dibatasi oleh bagian yang tidak Anda scale.
  • Jika p99 naik sementara p50 datar, ada yang terjadi sesekali: timeout menunggu pool, GC, satu instance yang lambat, CPU steal t3 di AWS.
  • Error saat high.js: 429 (limit_req Nginx atau limiter aplikasi — naikkan batas untuk test, atau yang Anda ukur hanyalah limiter), 502 (upstream crash/OOM), 504 (read timeout), timeout pool yang muncul sebagai 500.
  • task-processing.js: p95 POST /process tetap rendah meski submission melebihi kapasitas worker; queue yang menyerapnya. Queue depth bertambah sebesar (rate submit − rate proses); latency end-to-end ikut bertambah. Kapasitas worker untuk task sleep 1 detik ≈ worker × prefetch ÷ 1 detik = 8 task/detik. Submit 20/detik dan backlog bertambah 12 setiap detik.
  • Di AWS setelah ~30 menit beban: instance t3.small kehabisan CPU credit dan di-throttle ke baseline 20 %. Latency melonjak tanpa ada perubahan kode. Cek CPUCreditBalance di CloudWatch dan panel steal di Grafana.

Pulih?Traffic langsung berpindah; kapasitas kembali saat container di-start (kill = stop manual, tidak auto-restart)

Menghentikan worker

Apa yang gagalworker-1 dengan hingga 4 task sedang berjalan
Pengalaman userTidak ada di API. Beberapa task selesai lebih lambat dari perkiraan
Dideteksi olehRabbitMQ (koneksi tertutup), rabbitmq_detailed_queue_consumers turun ke 1; TargetDown
Pekerjaan yang sedang berjalanGraceful: task diselesaikan (≤ 25 detik). SIGKILL: message yang unacked di-requeue ke worker-2 (redelivered=true)
Message di queueAman; worker-2 menguras antrean dengan kecepatan setengahnya
Pulih?Ya. Task yang sudah di-claim worker-1 menunggu lease 60 detik expired, berputar lewat retry queue, lalu di-claim ulang
Data yang bisa hilangTidak ada. Pekerjaan mungkin dieksekusi dua kali (disengaja, write-nya idempotent)
Perbaikan di productionLease yang diperpanjang lewat heartbeat untuk task panjang; autoscaling consumer berdasarkan queue depth

Menghentikan Redis

Apa yang gagalCache dan penyimpanan rate limit
Pengalaman userRequest tetap berhasil; latency sedikit naik. Rate limiting diam-diam nonaktif (fail-open)
Dideteksi olehcache_operations_total{result="error"}, readiness "degraded", TargetDown untuk redis-exporter
Request yang sedang berjalanSetiap panggilan Redis gagal setelah ≤ 500 ms (socket timeout) lalu jatuh ke PostgreSQL
Message di queueTidak terpengaruh; invalidation dari worker gagal tanpa dampak
Pulih?Ya, otomatis; cache terisi kembali sesuai permintaan
Data yang bisa hilangIsi cache (memang disengaja). Jika Redis ter-partisi alih-alih restart, invalidation yang terlewat menyisakan entry stale sampai TTL (≤ 70 detik)
Perbaikan di productionReplica + failover (ElastiCache); circuit breaker untuk melewati Redis sepenuhnya setelah gagal berulang, alih-alih membayar 500 ms setiap kali; tentukan fail-open vs fail-closed per endpoint

Menghentikan RabbitMQ

Apa yang gagalMessage broker
Pengalaman userRead dan pembuatan task tetap jalan. POST /process mengembalikan 503 setelah publish timeout; task ditandai failed dengan last_error, sehingga client bisa mencoba lagi
Dideteksi olehException di publisher, tasks_published_total{result="error"}, readiness degraded, worker mencatat percobaan reconnect
Pekerjaan yang sedang berjalanWorker tidak bisa ack; message yang sedang diproses akan dikirim ulang setelah broker kembali (duplikat, diserap oleh claim)
Message di queueQueue durable + message persistent selamat di volume rabbitmq-data
Pulih?Ya: connect_robust reconnect dan mendeklarasikan ulang consumer; publisher API reconnect saat publish berikutnya
Data yang bisa hilangTidak ada yang sudah di-acknowledge. Message yang di-publish tanpa konfirmasi dilaporkan sebagai kegagalan, bukan dibuang diam-diam
Perbaikan di productionCluster 3 node dengan quorum queue, atau SQS; outbox agar submission tetap antre di lokal selama outage

Menghentikan PostgreSQL

Apa yang gagalSource of truth
Pengalaman userHampir semuanya gagal: autentikasi memuat user dari database. /health/ready mengembalikan 503
Dideteksi olehReadiness, alert rasio 5xx, TargetDown untuk postgres-exporter
Request yang sedang berjalanGagal dengan error koneksi; transaction tidak pernah di-commit
Message di queueTetap di queue. Worker yang menerimanya gagal claim, lalu nack(requeue=True) setelah 1 detik — message berputar tapi tidak hilang
Pulih?Ya, tanpa restart: pool_pre_ping mengganti koneksi yang mati
Data yang bisa hilangTidak ada yang sudah di-commit (synchronous_commit=on, WAL). Kehilangan disk di node data = semua data sejak backup terakhir — dan belum ada backup otomatis
Perbaikan di productionRDS Multi-AZ dengan failover otomatis; backup PITR; worker berhenti consume selama DB mati alih-alih berputar

Kill container (SIGKILL)

docker kill melewati graceful shutdown: tanpa draining, tanpa ack terakhir, transaction yang terbuka dibatalkan. Setiap komponen stateless pulih lewat requeue, retry, atau rollback. Untuk yang stateful, ini menguji crash safety: PostgreSQL me-replay WAL saat start (database system was interrupted; last known up at …, lalu ready to accept connections); RabbitMQ memulihkan queue durable dari message store-nya. Perhatikan bahwa Docker tidak me-restart container yang di-kill secara manual — crash sungguhan (atau OOM kill) yang memicu restart: unless-stopped.

Menghabiskan memori

Apa yang gagalcgroup worker-1 mencapai 512 MB (scripts/chaos.sh memory-worker)
Pengalaman userTidak langsung terasa; task di worker itu tertunda
Dideteksi olehKernel OOM killer (journalctl -k), OOMKilled=true / exit 137, jumlah restart

Pengalaman userDelay DB: setiap request lebih lambat; di bawah beban, koneksi pool tertahan 300 ms+ masing-masing → pool habis → request menunggu 5 detik → error 500. Perlambatan kecil berubah menjadi outage

Skenario khusus AWS

  • Stop EC2 instance node app: api-2 dan api-3 hilang bersamaan; koneksi timeout (host yang mati tidak mengirim RST) → setiap failover memakan proxy_connect_timeout (3 detik) sampai ditandai down. Perhatikan betapa berbedanya ini dibanding container yang di-stop.
  • Stop NAT instance: traffic live tidak terpengaruh; SSM agent offline setelah beberapa menit; deploy gagal dengan “no instances matched”. Egress dan control plane adalah failure domain yang terpisah.
  • Hapus rule sg-data untuk sg-app: readiness api-2/api-3 gagal dengan timeout; api-1 tetap jalan. Kegagalan murni konfigurasi yang terlihat seperti outage database.

Biaya minimal vs mirip production

Belajar minimal (~$20/bulan, ~$0,03/jam)

  • 1 × t3.small menjalankan seluruh docker-compose.yml (langkah 24)
  • Public subnet di default VPC, SG 80/443 + SSH dari IP Anda
  • Elastic IP + Let’s Encrypt
  • Mengajarkan: Linux, Docker, TLS, SG, DNS

Mirip production (~$500+/bulan)

  • ALB di 2 AZ, ASG berisi 2+ instance app (atau ECS Fargate)
  • RDS PostgreSQL Multi-AZ, ElastiCache dengan replica, Amazon MQ/SQS
  • NAT Gateway per AZ, VPC endpoint, WAF
  • Managed Prometheus/Grafana atau CloudWatch, backup otomatis

Pelajaran yang diajarkan sistem ini

  1. Distribusi memberi kapasitas dan isolasi, dengan harga partial failure. Lima server berarti lebih banyak cara untuk rusak, bukan lebih sedikit.
  2. Stateless murah untuk di-scale; state adalah tempat engineering yang sesungguhnya. Setiap masalah sulit menyentuh PostgreSQL atau RabbitMQ.
  3. Setiap network call butuh timeout, dan setiap retry butuh backoff, jitter, dan idempotency — jika tidak, retry itu sendiri yang menjadi outage.
  4. At-least-once delivery + pemrosesan idempotent adalah cara “exactly once” dibangun dalam praktik.
  5. Dua penyimpanan berarti ada keputusan consistency. TTL cache, commit-lalu-publish, status yang eventual: masing-masing adalah trade-off yang disengaja.
  6. Health check adalah bagian dari failure model. Liveness vs readiness, dan apa saja yang menjadi dependency readiness, menentukan apakah partial failure menyebar.
  7. Jaringan gagal sebagai timeout, proses gagal sebagai refused. Tahu mana yang sedang Anda hadapi memangkas waktu debugging separuhnya.
  8. Keamanan itu berlapis, dan lapisannya punya celah: SG, host firewall, auth aplikasi — dan celah seperti Docker yang melewati ufw atau IMDS yang bisa dijangkau dari container.
  9. Role, bukan key. OIDC dan instance profile menghilangkan penyebab kebobolan akun AWS yang paling umum.
  10. Artifact immutable membuat rollback membosankan — kecuali untuk data dan secret, yang tinggal di luarnya.
  11. Metrics menjawab “seberapa parah”, log menjawab “apa yang terjadi”, trace menjawab “di mana”. Correlation ID membuat log bisa dipakai lintas mesin.
  12. Hasil scaling jarang linear. Bagian yang menarik adalah menemukan bottleneck berikutnya.
  13. Menambah teknologi itu mudah; membenarkannya adalah keterampilan. Arsitektur termurah yang memenuhi kebutuhan adalah arsitektur terbaik.
