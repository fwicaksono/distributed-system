Request validation dan response model

extra="forbid" menolak field yang tidak dikenal (salah ketik menjadi error, bukan data yang diam-diam diabaikan). response_model=TaskRead di route berarti kolom internal seperti lease_expires_at tidak akan pernah bocor, meskipun object ORM-nya memiliki kolom itu.

Dependency injection

Route mendeklarasikan apa yang dibutuhkan; FastAPI membangunnya per request dan meng-cache setiap dependency dalam request itu (satu session dipakai bersama oleh lookup user dan service). Dependency session berbentuk generator: kode setelah yield melakukan commit atau rollback — pola unit of work.

Middleware, error, logging, konfigurasi

  • Middleware (app/middleware/request_context.py) membungkus setiap request: memakai ulang X-Request-ID dari Nginx, mengukur durasi, mencatat metrics Prometheus dengan label route template, dan menulis satu baris access log JSON.
  • Error handling (app/core/exceptions.py): service melempar NotFoundError, ConflictError, dan seterusnya; satu handler memetakannya ke status code dan satu bentuk error yang menyertakan request_id. Exception yang tidak tertangani di-log beserta stack trace dan dikembalikan sebagai 500 generik.
  • Konfigurasi (app/core/config.py): setiap setting adalah environment variable yang divalidasi Pydantic saat startup. Secret yang hilang membuat container langsung crash — jauh lebih baik daripada gagal di request sungguhan pertama.
  • Connection pooling (app/core/database.py): satu pool per proses, dibuat di lifespan. pool_size=5, max_overflow=5, pool_timeout=5s, pool_pre_ping=True, dan statement_timeout di sisi server.

FastAPI menjalankan endpoint async def di satu event loop per proses. Pemanggilan yang blocking di dalamnya — time.sleep, requests.get, hashing bcrypt — membekukan semua request di proses itu. Karena itulah AuthService melakukan hashing password dengan asyncio.to_thread.

Transaction dan isolation dalam praktik

Dua user menekan “process” bersamaan dan request-nya jatuh ke api-1 dan api-3. Keduanya menjalankan:

UPDATE tasks SET status = 'queued', attempts = 0 WHERE id = $1 AND owner_id = $2 AND status IN ('pending', 'failed') RETURNING *;

Isolation default PostgreSQL adalah READ COMMITTED. UPDATE pertama mengunci row; UPDATE kedua menunggu, lalu mengevaluasi ulang WHERE terhadap row yang sudah di-commit, menemukan status='queued', dan meng-update nol row → service mengembalikan 409. Tanpa lock eksplisit, tanpa race condition — sebuah compare-and-set dalam satu statement. claim() di worker memakai teknik yang sama.

REPEATABLE READ / SERIALIZABLE dibutuhkan ketika keputusan bergantung pada beberapa row yang dibaca sebelumnya dalam transaction (misalnya “hanya jika user punya kurang dari 10 task aktif”). Level ini bisa gagal dengan serialization error yang harus di-retry. Jika aturannya bisa diekspresikan, utamakan conditional write dalam satu statement.

Connection pooling dan migration

Setiap koneksi PostgreSQL adalah proses server tersendiri (~5–10 MB). Anggarannya: 3 API × 10 + 2 worker × 10 + exporter ≈ 55, di bawah max_connections=100. Menambah API ke-4 tanpa menghitung ulang angka ini adalah awal dari banyak outage. Pada skala lebih besar, pasang PgBouncer dalam transaction mode di antara aplikasi dan database.

Migration dijalankan sebagai one-off job terpisah (docker compose run --rm migrate) sebelum kode baru di-roll out — jangan pernah dari setiap API saat startup, karena tiga replika akan saling berebut. Tulis migration yang backward compatible (expand → deploy → contract): tambahkan kolom nullable, deploy kode yang memakainya, lakukan backfill, lalu terapkan NOT NULL di release berikutnya.

Kenapa Redis lebih cepat

Datanya ada di RAM; GET hanyalah lookup hash table tanpa parsing, query planning, locking, atau disk. Sisa ~0,2 ms kebanyakan adalah network round trip. PostgreSQL dengan cache yang hangat juga cepat (~1 ms) — keuntungan utamanya bukan “kecepatan”, melainkan mengurangi beban database, yang punya batas koneksi keras.

Layak di-cache

  • Data yang sering dibaca dan jarang berubah: detail task
  • Hasil komputasi yang mahal
  • Data yang boleh stale ≤ 60 detik

Jangan di-cache

  • Status task — client melakukan polling justru untuk melihat state terbaru
  • Keputusan authorization dan saldo
  • List ber-pagination — invalidation lintas halaman sulit
  • Apa pun yang lebih murah dihitung daripada di-invalidate dengan benar

TTL, stale data, invalidation, stampede

  • TTL membatasi seberapa stale data bisa: meskipun ada invalidation yang terlewat, entry akan hilang dalam 60–70 detik. Jitter mencegah key yang ditulis bersamaan kedaluwarsa bersamaan.
  • Invalidation adalah DEL setelah commit ke database. Menghapus sebelum commit membuat reader yang berjalan bersamaan bisa meng-cache ulang row lama. Masih ada race kecil (reader memuat row lama → writer commit + delete → reader menulis nilai lama); TTL adalah jaring pengamannya.
  • Cache stampede: key populer kedaluwarsa dan 500 request miss bersamaan, semuanya menghantam PostgreSQL. SET lock NX PX 2000 yang singkat membuat hanya satu request yang memuat ulang, sementara yang lain menunggu 50 ms lalu membaca cache lagi.
  • Penanganan kegagalan Redis: setiap panggilan Redis menangkap error, menaikkan cache_operations_total{result="error"}, lalu jatuh ke PostgreSQL. Socket timeout 500 ms sehingga Redis yang hang hanya memakan setengah detik, bukan tiga puluh.

Kenapa perlu broker, dan kapan tidak

Tanpa queue, POST /process akan mengerjakan tugasnya secara langsung: client menunggu, read timeout Nginx 30 detik memutus task yang lama, lonjakan traffic membebani CPU API, dan deploy membunuh pekerjaan yang sedang berjalan. Dengan RabbitMQ, API meng-commit niatnya, mem-publish message, dan mengembalikan 202 dalam hitungan milidetik; worker menarik pekerjaan sesuai kemampuannya; pekerjaan yang belum selesai selamat dari crash.

Kapan tidak perlu: jika pekerjaan selesai < 1 detik, kerjakan langsung saja. Jika butuh histori event yang bisa di-replay, gunakan Kafka. Jika di AWS dan tidak ingin mengoperasikan broker, SQS memberi hampir semua ini tanpa server. Tabel PostgreSQL dengan SELECT … FOR UPDATE SKIP LOCKED adalah queue yang sangat layak untuk volume sedang — dan menghilangkan masalah dual-write di bawah.

Masalah dual-write

Database dan broker tidak bisa berbagi satu transaction. Commit-lalu-publish berarti crash di antara keduanya membuat task tetap queued tanpa message. Publish-lalu-commit lebih buruk: worker bisa menerima message untuk row yang belum terlihat. Transactional outbox memperbaikinya: insert row outbox di transaction yang sama; sebuah relay mem-publish row outbox lalu menandainya terkirim. Ini dicatat sebagai improvement agar Anda bisa mengimplementasikannya setelah melihat celahnya sendiri.

Total delay retry (5 + 30 + 120 = 155 detik) harus lebih besar dari lease (60 detik) — worker menolak start jika tidak. Insert hasil memakai ON CONFLICT (task_id) DO NOTHING, sehingga dua penyelesaian pun hanya menulis satu hasil.

Graceful shutdown

Saat menerima SIGTERM (dari docker stop), worker membatalkan consumer-nya (tidak menerima message baru), menunggu task yang sedang berjalan hingga 25 detik, lalu menutup koneksi. Docker menunggu stop_grace_period: 30s sebelum SIGKILL. Message yang masih unacked di-requeue oleh RabbitMQ saat koneksi tertutup — tidak ada yang hilang, paling-paling duplikat, dan itu diserap oleh claim().

Concurrency

Membuat banyak pekerjaan maju dalam rentang waktu yang tumpang tindih, tidak harus di detik yang sama. Satu koki dengan empat panci: aduk satu, sementara yang lain mendidih. Ideal untuk menunggu (jaringan, disk).

Parallelism

Mengeksekusi banyak pekerjaan di detik yang sama pada core berbeda. Empat koki. Dibutuhkan untuk komputasi (hashing, pemrosesan gambar).

Penerapannya

  • FastAPI: satu proses uvicorn per container menangani ratusan request bersamaan karena sebagian besar waktunya dihabiskan menunggu PostgreSQL/Redis. Menambah kapasitas CPU = menambah container, bukan menambah thread.
  • RabbitMQ consumer: prefetch_count=4 berarti setiap worker menangani hingga 4 task sekaligus. Untuk task sleep, keempatnya berjalan concurrent di satu core; throughput ≈ 2 worker × 4 / durasi task.
  • Background worker: task hash berjalan di process pool (2 proses): benar-benar paralel, tapi maksimal sebanyak jumlah core. Mengatur prefetch 50 untuk pekerjaan CPU hanya memindahkan antrean ke dalam worker, padahal di RabbitMQ message itu bisa diambil worker lain.

Horizontal vs vertical scaling
Vertical: mesin yang lebih besar (sederhana, ada batas atas, butuh downtime). Horizontal: lebih banyak mesin (tanpa batas untuk tier stateless, butuh load balancing dan state bersama). Di sini API di-scale horizontal; PostgreSQL di-scale vertical.
Stateless vs stateful
Instance API tidak menyimpan apa pun yang dibutuhkan request berikutnya — session berupa JWT, counter di Redis, data di PostgreSQL — jadi instance mana pun bisa melayani request apa pun. PostgreSQL dan RabbitMQ menyimpan data dan tidak bisa ditukar sembarangan.
Service-to-service communication
Synchronous (HTTP Nginx→API, SQL, Redis): sederhana, tapi pemanggil menunggu dan ikut gagal bersama yang dipanggil. Asynchronous (AMQP): pemanggil tidak menunggu, dengan harga hasil yang eventual dan kemungkinan duplikat.
Network failure & partial failure
Redis bisa tidak terjangkau dari api-2 sementara api-1 masih bisa. Kode harus menganggap “satu dependency ini mati” sebagai kondisi normal (cache fail-open, readiness degraded).
Timeout
Satu-satunya cara membedakan “lambat” dan “mati”. Setiap hop punya timeout: Nginx connect 3 detik / read 30 detik, pool 5 detik, statement 5 detik, Redis 0,5 detik, publish 5 detik, health check 2 detik.
Retry & exponential backoff
Retry langsung melipatgandakan beban pada service yang sedang kesulitan. Backoff menggandakan waktu tunggu; jitter mengacaknya (app/utils/retry.py, retry queue RabbitMQ 5/30/120 detik).
Idempotency
Retry hanya aman jika mengulang operasi tidak berbahaya: conditional UPDATE, ON CONFLICT DO NOTHING, lease.
Fault tolerance
Tetap beroperasi meski sebagian komponen gagal: dua worker, tiga API, Redis fail-open.
Availability vs reliability
Availability: persentase waktu sistem menjawab (99,9 % ≈ 43 menit mati per bulan). Reliability: sistem menjawab dengan benar — sistem yang cepat mengembalikan data stale itu available tapi tidak reliable.
Consistency & eventual consistency
PostgreSQL memberi strong consistency per transaction. Status task eventually consistent dengan “pekerjaannya”: queued sekarang, completed beberapa detik kemudian. Cache eventually consistent dengan PostgreSQL, dibatasi TTL.
CAP theorem secara praktis
Saat terjadi network partition, penyimpanan yang direplikasi harus memilih: menolak sebagian request (consistency) atau menjawab dengan data yang mungkin stale (availability). Di sini hanya ada satu PostgreSQL, jadi partition dari node data berarti unavailable — secara konstruksi kita memilih C. Cache Redis adalah pilihan bernuansa AP: menyajikan data yang mungkin stale daripada gagal. Di luar partition, trade-off sehari-harinya adalah latency vs consistency (PACELC).
