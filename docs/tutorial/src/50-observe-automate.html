Monitoring memeriksa failure mode yang sudah diketahui terhadap threshold: “error rate > 5 %”. Observability adalah sifat sistem yang memungkinkan Anda menjelaskan kegagalan yang belum diketahui dari output-nya: “kenapa hanya task milik user yang dibuat Selasa lalu yang lambat?”. Monitoring adalah sesuatu yang Anda lakukan; observability adalah sesuatu yang dimiliki sistem. Alerting mengubah monitoring menjadi tindakan — kirim alert untuk gejala yang dirasakan user, bukan untuk setiap penyebab kecil.

Cara kerja Prometheus

Setiap target mengekspos /metrics dalam bentuk teks. Prometheus menarik (pull) data itu setiap 15 detik, menyimpan sampelnya di time-series database lokal, mengevaluasi rule, dan melayani query PromQL. Target yang berhenti menjawab mendapat nilai up == 0: ketiadaan data pun terdeteksi, sesuatu yang tidak bisa dilakukan model push.

Cara kerja rollback

  1. Otomatis, per host: deploy.sh menunggu container healthy dan memverifikasi endpoint. Jika gagal, ia mengarahkan ulang /opt/taskplatform/current ke release sebelumnya dan men-deploy-nya, lalu menggagalkan SSM command, sehingga pipeline ikut gagal.
  2. Manual, seluruh fleet: jalankan workflow rollback dengan SHA sebelumnya. Karena image immutable, tidak ada yang di-build ulang — kode dan konfigurasi kembali persis.
  3. Database: tidak di-rollback. Migration mengikuti pola expand/contract sehingga release sebelumnya tetap berjalan dengan schema baru. Migration destruktif (drop kolom) baru dikirim setelah tidak ada release aktif yang membacanya.

Alternatif: blue/green (dua environment penuh, pindahkan traffic — butuh kapasitas ganda atau load balancer yang bisa memindahkan traffic), canary (kirim 5 % traffic ke versi baru, bandingkan metrics — butuh weighted routing dan metrics yang baik).

Buktikan rolling update tanpa downtime

# Terminal 1: traffic konstan, cetak setiap response selain 200 while true; do c=$(curl -s -o /dev/null -w '%{http_code}' https://api.example.com/health/live); [ "$c" != 200 ] && date +%T" $c"; sleep 0.1; done # Terminal 2: picu deploy git commit --allow-empty -m "rolling deploy test" && git push

Yang diharapkan: terminal 1 tidak mencetak apa pun untuk request GET. Kenapa bisa: uvicorn menguras request yang sedang berjalan saat SIGTERM; Nginx me-retry GET yang mengenai container yang sedang restart; hanya satu dari tiga upstream yang restart pada satu waktu. Celah yang tersisa: edge membuat ulang container Nginx itu sendiri, yang memutus koneksi sekitar satu detik — setup production memakai nginx -s reload untuk perubahan konfigurasi saja, atau load balancer di depannya.

Liveness lolos (prosesnya berjalan) tetapi readiness gagal (tidak bisa menjangkau PostgreSQL) — persis perbedaan yang dibahas di langkah 6. Karena file compose ikut di dalam image, rollback ke image sebelumnya memulihkan POSTGRES_HOST yang benar. Node edge tidak pernah tersentuh: pipeline berhenti di 8d. Revert commit tersebut di main setelahnya.

Secret dan parameter tinggal di Parameter Store, di luar image. Seandainya yang dirusak adalah /taskplatform/prod/POSTGRES_PASSWORD, rollback akan me-render nilai rusak yang sama dan ikut gagal. Karena itulah hanya secret yang tinggal di luar release, dan histori Parameter Store penting: aws ssm get-parameter-history --name /taskplatform/prod/POSTGRES_PASSWORD --with-decryption.

Perhatikan juga jendela waktunya: antara api-2 baru start dan rollback, Nginx mengirim request ke instance yang live tapi belum ready. Nginx OSS tidak punya active readiness check; health check target group ALB pada /health/ready akan menjauhkannya dari rotasi.
